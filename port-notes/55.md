# PHP 5.5.38 backport notes — "Avoid state corruption via bailout"

CVE-2026-109618 (GHSA-w8hw-w9fx-j79w) + CVE-2026-109619 (GHSA-6wmf-4rv5-p3rp)

**UNOFFICIAL analogy backport.** PHP 5.5 is EOL and got no official patch. 5.5 uses the
OLD Zend engine (old `zend_mm` allocator, old `HashTable` with `arBuckets`, no
`zend_string`, `TSRMLS_*` threading). This is therefore a **port by analogy** of upstream
commit `712e60f9` (shipped on the 7.x branches), not a direct diff application. The
defensive intent is kept identical; the code is adapted to 5.x idioms. Not vendor-reviewed;
apply at your own risk on your own EOL servers.

- Patch: `scratchpad/patches/php-5.5.patch` (8 files, 25 hunks, `patch -p1 --forward --batch`, no `.rej`)
- Source: php-5.5.38.tar.gz, sha256 `4f458c9b504269615715a62f182b7c2f89bb8284f484befc221b56a1571b506e` (verified before extract)
- Build base image: `btport-55` = `debian:buster` (gcc-8), native arm64, archived apt mirrors.

Reference cross-check: the sibling 5.6 port was not present on disk during this work
(`patches/php-5.6.patch` / `port-notes/56.md` absent), so every hunk was derived and
verified directly against the 5.5.38 source. The 5.6.40 tree in `inspect5x/` was used only
to confirm the two 5.x releases are structurally identical for the touched files (they are;
`Zend/zend_alloc.c` even shares line numbers).

## MAPPED / ADAPTED items (what the patch does)

### CVE-2026-109618 — OOM/overflow must not longjmp out of a half-initialized request

1. **`Zend/zend_alloc.c` — new `zend_mm_safe_error_ex()` + rewritten `zend_mm_safe_error()`.**
   Upstream's core fix replaces the `zend_bailout()` (longjmp) OOM path with a function
   that prints the fatal message and `_exit(1)`s. 5.5's `zend_mm_safe_error()` ended with a
   `zend_try { zend_error_noreturn(...) } zend_catch {}` block followed by `zend_bailout()`.
   - Added a variadic `static ZEND_NORETURN zend_mm_safe_error_ex(const char *format, ...)`
     that reuses 5.5's **own** location logic (`zend_is_compiling()` /
     `zend_get_compiled_filename()` else `EG(in_execution)` + `EG(active_op_array)->filename`
     / `EG(opline_ptr)`), prints `"\nFatal error: <msg> in <file> on line <n>\n"` via
     `vfprintf`, and calls `_exit(1)`. (Variadic + `vfprintf` so the one helper serves both
     the 2-arg OOM calls and the 3-arg overflow calls, mirroring upstream's signature.)
   - `zend_mm_safe_error()` now just frees `heap->reserve` (kept, as the 5.5 original did)
     and tail-calls `zend_mm_safe_error_ex(...)`. No more `zend_try`/`zend_bailout`.
   - Adaptation vs 7.x: 7.x uses `zend_is_executing()`/`zend_get_executed_filename_ex()`/
     `ZSTR_VAL`; those do not exist in 5.5, so the 5.5 location idiom is used instead.
     The helper is exported `ZEND_API` (see item 3a) so it also covers the `zend_strtod.c`
     Balloc site, matching upstream's shape and the 5.4 sibling port.
   - Added `#include <stdarg.h>` (the file only used `va_list` under `#if ZEND_DEBUG`, so the
     include was not otherwise guaranteed in a non-debug build). `_exit` comes from
     `<unistd.h>`, already included under `HAVE_UNISTD_H`.

2. **`Zend/zend_alloc.c` — integer-overflow allocation sites redirected.** All six
   `safe_address()` arch variants (i386/x86_64/arm/aarch64/32-bit-llong/portable) called
   `zend_error_noreturn(E_ERROR, "Possible integer overflow in memory allocation ...")`,
   which reached the same longjmp. All six now call `zend_mm_safe_error_ex(...)`. (On arm64
   only the `__aarch64__` variant compiles; the rest are patched for correctness/portability.)

3. **`Zend/zend_alloc.c` — `zend_mm_panic()` `exit(1)` → `_exit(1)`.** Matches upstream's use
   of `_exit` to skip atexit/handlers on a corrupted heap.

3a. **`zend_mm_safe_error_ex()` exported + `Zend/zend_strtod.c` Balloc covered** (parity with the
   5.4 sibling port — added per cross-version-consistency follow-up). The helper is now `ZEND_API`:
   declared in `Zend/zend_alloc.h` (noreturn, guarded exactly as `zend.h` guards
   `zend_error_noreturn`) and defined `ZEND_API` in `zend_alloc.c`, so it is callable cross-TU.
   `Balloc()`'s malloc-failure site in `zend_strtod.c` — `zend_error(E_ERROR, "Balloc() failed to
   allocate memory")`, which on `E_ERROR` also bails out — is redirected to
   `zend_mm_safe_error_ex("Balloc() failed to allocate memory")`; this is exactly the "longjmp out
   of an allocation failure" class the CVE targets. No include was added: `zend.h` (which includes
   `zend_alloc.h`) is already in scope in `zend_strtod.c`. 5.5 has only ONE such malloc-failure
   site (7.x has two, behind an `Omit_Private_Memory` `#if/#else` that 5.5 lacks). The other
   `zend_error` in `Balloc()` — `"Balloc() allocation exceeds list boundary"` (a `k > Kmax` bounds
   assertion fired *before* any allocation) — is NOT an OOM path and is intentionally left as-is.

4. **`main/rfc1867.c` — `max_multipart_body_parts` INI + enforcement** (closes the
   OOM-reaching multipart strategy for both CVEs).
   - New INI `max_multipart_body_parts` (default `-1`) registered in `main/main.c`.
   - `rfc1867_post_handler`: reads `INI_INT("max_multipart_body_parts")`; when `< 0` it
     defaults to `PG(max_input_vars) + upload_cnt`; decremented once per body part (inside
     the `Content-Disposition` block, exactly where upstream placed it); on underflow it
     emits `E_WARNING "Multipart body parts limit exceeded ..."` and `goto fileupload_done`.
     `body_parts_cnt`/`body_parts_limit` declared at the top of the function (C89-clean, 5.x
     style) instead of mid-block as in the 7.x diff.
   - `multipart_buffer_headers`: header whitelist + dedup — only `Content-Disposition` /
     `Content-Type` are kept, duplicates ignored, via new `php_mime_should_save_hdr()` + a
     forward decl of `php_mime_get_hdr_value()` and an existing-value lookup. `isspace` arg
     cast to `(unsigned char)`. Adapted to 5.5's `smart_str` (upstream 7.x uses `smart_string`).
   - `substring_conf`: `int len`/`int i` → `size_t`; the `strend - str` caller cast to
     `(size_t)`. (5.5's `strlen(str)` caller already had no `(int)` cast to remove.)

### CVE-2026-109619 — stale request-owned global state must be reset

5. **`ext/session/session.c` — `php_session_rfc1867_callback` neutralised.**
   `if (!PS(rfc1867_enabled))` → `if (!PS(rfc1867_enabled) || 1)` (C89: `1`, not `true`),
   so the session upload-progress producer/consumer early-returns unconditionally. Matches
   upstream intent of disabling the demonstrated early producer/consumer.

6. **`main/SAPI.c` — `sapi_deactivate()` NULLs freed request pointers.** After each
   `efree()` of `auth_user`, `auth_password`, `auth_digest`, `content_type_dup`,
   `current_user`, the field is set to `NULL`. In 5.5 none of these five were NULLed here,
   so all five NULLs were added (upstream notes 7.x already NULLed some — not the case in 5.5).

7. **`main/main.c` — `php_request_shutdown()` resets super-global + module state.**
   - In the "Destroy super-globals" loop, after `zval_ptr_dtor(&PG(http_globals)[i])` the slot
     is set `PG(http_globals)[i] = NULL`. This is the 5.x analogue of upstream's `ZVAL_UNDEF`:
     5.5 stores `zval*` guarded by `if (PG(http_globals)[i])`, and the dtor does not clear the
     pointer, so without the reset the guard would re-read a dangling pointer on the next
     request before `php_request_startup()` re-initialises it. Setting `NULL` makes the guard
     safe. (The 5X brief flagged this as "record if already null-guarded"; the guard reads but
     never *resets* the pointer, so the NULL reset is the actual fix and is included.)
   - `PG(modules_activated) = 0;` added at the very end of `php_request_shutdown()` (not
     already set there).

8. **`Zend/zend_llist.c` — `zend_llist_destroy()` clears `head`/`tail`.** Added
   `l->head = NULL; l->tail = NULL;` before `l->count = 0;` so freed list state cannot be
   reused. Direct 1:1 map.

## N/A items (recorded, deliberately NOT forced) — with reasons

- **`array_init_singleton` / `zend_new_array_singleton` / `HT_HASH_RESET` small-table guard**
  (upstream `zend_API.h`, `zend_hash.c/.h`, `zend_types.h`, `main/php_variables.c`): 5.5 uses
  the OLD `HashTable` (`Bucket **arBuckets`), has no `zend_string` and no SIMD `HT_HASH_RESET`.
  The over-read these guard against does not exist in 5.5. Skipped entirely.
- **`zend_vm_def.h` / `zend_vm_execute.h` CONCAT length guards**: 5.5's VM and CONCAT handlers
  predate `zend_string`/`ZSTR_*`; the 7.x `ZSTR_LEN > ZSTR_MAX_LEN - ...` guard has no direct
  5.5 analogue and the integer-overflow protection for string growth is already provided by the
  redirected `safe_address`/`zend_mm_safe_error_ex` path (item 2). Not forced (brief says do not
  guess the VM change).
- **`Zend/zend_multiply.h` overflow sites**: in 5.5 these sites live in `zend_alloc.c`'s
  `safe_address()` (item 2), not in `zend_multiply.h` (which has none). Covered via item 2.
- **`_estrdup` / `_estrndup` / `zend_strndup` `"(1 * %zu + 1)"` overflow checks**: these
  `length + 1 == 0` guards do not exist in 5.5 at all, so there is nothing to redirect.
- **`zend_out_of_memory()` `exit`→`_exit`**: function does not exist in the 5.5 allocator. Only
  `zend_mm_panic` applies (item 3).
  (The `Zend/zend_strtod.c` `Balloc()` malloc-failure site, previously listed here as N/A, is now
  MAPPED — see item 3a — after exporting the helper as `ZEND_API`, for parity with the 5.4 port.)
- **`shutdown_executor()` user-handler / object-store resets** (upstream `zend_execute_API.c`):
  those reference 7.x `EG()` fields (`user_error_handlers`, `objects_store.object_buckets`, the
  `ZVAL_UNDEF(&EG(user_error_handler))` model) that differ in 5.5's engine. The equivalent
  request-state hygiene for 5.5 is covered by items 5–8 (session callback, SAPI auth pointers,
  http_globals, modules_activated, llist). Not force-ported to avoid touching 5.5 executor
  internals without a verified analogue.

## VALIDATION

Build base: Docker image `btport-55` = `debian:buster` (gcc-8), native arm64, archived apt.
Configure (both trees, identical):
`./configure --disable-all --enable-cli --enable-session --enable-ctype --enable-tokenizer --with-pcre-regex`.
`CFLAGS="-O2 -g1 -fno-strict-aliasing"`.

**Build-environment note (NOT part of the security patch):** at `-O0`, pristine 5.5.38 fails
to assemble on arm64 — `Zend/zend_multiply.h`'s aarch64 `ZEND_SIGNED_MULTIPLY_LONG` inline asm
uses loose `"X"` operand constraints, so gcc feeds `mul`/`smulh` stack-memory operands the
assembler rejects (`operand 2 must be an integer register`). This is a latent 5.5 arm64 bug,
present in the pristine tree and unrelated to this CVE work; building at `-O2` makes gcc keep
those operands in registers and both trees compile. No source workaround was applied and
`zend_multiply.h` is **not** touched by the patch. (Per the brief's "fall back rather than
hack the source" rule, the fallback here is the optimisation level, since no older base fixes
an asm-constraint bug on arm64.)

### Gate (a) — patch applies
`patch -p1 --forward --batch` on a pristine php-5.5.38 tree: **clean, 8 files, 25 hunks, no `.rej`/`.orig`**
(verified on the macOS host and again inside the container).

### Gate (b) — compiles
- pristine: configure exit 0, `make -j4` exit **0**, 8 warnings.
- patched:  configure exit 0, `make -j4` exit **0**, 8 warnings.
- The patched warning set is **byte-identical** to pristine (diff empty). The only warning that
  touches a patched file (`ext/session/session.c:866`, an incompatible-pointer warning) is
  pre-existing and far from the change at line 2623. **The patch introduces zero new warnings.**

### Gate (c) — make test (pristine vs patched), `NO_INTERACTION=1`
Same corpus both runs: Number of tests 13270 (7449 executed), skipped 5821, warned 1.
(Numbers below are from the re-validation **after** the Balloc/`ZEND_API` change — identical to the
pre-Balloc run: the strtod change adds no new test delta.)

| run      | passed | failed |
|----------|--------|--------|
| pristine | 7415   | 3      |
| patched  | 7406   | 12     |

The 3 failures common to both — `getservbyname_basic`, `getservbyport_basic`,
`getservbyport_variation1` (ext/standard) — are **pre-existing** `/etc/services`-dependent
environment failures, present identically in the pristine tree; not caused by the patch.

The **+9** patched-only failures are all **direct, intended effects of the two mitigations**,
each confirmed from the test `.diff` — exactly the "expected OOM/rfc1867 deltas" the brief
anticipated, not unintended regressions:
- **8 × `ext/session/tests/rfc1867*.phpt`** (`rfc1867`, `rfc1867_inter`, `rfc1867_sid_cookie`,
  `rfc1867_sid_get`, `rfc1867_sid_get_2`, `rfc1867_sid_invalid`, `rfc1867_sid_only_cookie`,
  `rfc1867_sid_post`): `.diff` shows the expected `$_SESSION` upload-progress `array(5){...}`
  is now `NULL`. This is item 5 — `php_session_rfc1867_callback` deliberately early-returns
  (`|| 1`), so progress is never recorded. The upstream fix neutralises the same callback, so
  these tests fail on the officially-patched branches too.
- **1 × `tests/lang/bug45392.phpt`** (ob_start/ob_end_clean under `memory_limit=100`): `.diff`
  is a single extra leading blank line. The test still hits "Allowed memory size ... exhausted",
  but it now travels item 1's path (`zend_mm_safe_error_ex` prints `"\nFatal error: ..."` and
  `_exit(1)`) instead of the old catchable `zend_bailout`. The leading `\n` (same as upstream's
  helper) shifts the exact `EXPECTF` output by one blank line. This is precisely the OOM-path
  behaviour change the fix intends.

No test that pristine passed newly fails for any reason **other than** these two documented
mitigations.

### Gate (d) — behavioural (patched tree)
- `nm sapi/cli/php | grep zend_mm_safe_error_ex` → `000000000020a9e0 T zend_mm_safe_error_ex`
  (global text symbol).
- `nm -D sapi/cli/php | grep zend_mm_safe_error_ex` → `000000000020a9e0 T zend_mm_safe_error_ex`
  — now a **dynamic/exported** symbol, confirming the `ZEND_API` export (item 3a).
- `grep zend_strtod.c` → the Balloc malloc-failure site now reads
  `zend_mm_safe_error_ex("Balloc() failed to allocate memory")`; the only remaining `zend_error`
  in `Balloc()` is the unrelated `"allocation exceeds list boundary"` bounds assertion (out of scope).
- `grep zend_bailout Zend/zend_alloc.c` → only a comment line remains; **no `zend_bailout()` call
  on the OOM/overflow path**.
- `strings sapi/cli/php | grep 'Multipart body parts'` → the limit-exceeded message is compiled in.
- `php -i | grep max_multipart_body_parts` → `max_multipart_body_parts => -1 => -1` (new INI,
  default present); `php -d max_multipart_body_parts=7 -i` → `=> 7 => 7` (SYSTEM|PERDIR INI parses).
- **End-to-end part-limit (built-in server, real multipart POST of 10 parts):**
  - `max_multipart_body_parts=100` → handler returns `PARTS_POST=10` (all parsed).
  - `max_multipart_body_parts=5`   → handler returns `PARTS_POST=5` (parsing **truncated**; the
    per-part decrement hit the limit and `goto fileupload_done` fired).
  - Honest caveat: the `E_WARNING "Multipart body parts limit exceeded"` text was **not** captured
    in the built-in server's main stderr log (that SAPI emits per-request warnings into the
    worker/response path, not the master stderr file). The 10→5 truncation is the definitive
    proof that the limit check and the `goto fileupload_done` executed; the warning string itself
    is verified present in the binary via `strings`.

### Honest caveats / scope
- Unofficial, not vendor-reviewed; analogy backport to an EOL branch.
- Validation was done with a minimal `--disable-all` CLI+session build; extensions not built were
  not exercised. The core, session, SAPI and rfc1867 paths the fix touches are all covered.
- The multipart limit was proven via the CLI built-in web server, not php-fpm; behaviour is the
  same `rfc1867_post_handler` code path.
- `-O2` was required to build on arm64 (see build-environment note); on an x86 or older-assembler
  host `-O0` would also build. This does not affect the patch contents.
