# PHP 5.6.40 backport notes — "Avoid state corruption via bailout"

**CVE-2026-109618 (GHSA-w8hw-w9fx-j79w)** + **CVE-2026-109619 (GHSA-6wmf-4rv5-p3rp)**

> **This is an UNOFFICIAL, by-analogy backport.** PHP 5.6 is EOL and received no
> upstream fix. 5.6 uses the OLD Zend engine (old `zend_mm` allocator, old `HashTable`
> with `Bucket **arBuckets`, no `zend_string`, `TSRMLS_*` thread macros), so this is NOT
> a diff of the official 7.4 commit (`712e60f9edfd03f0960fc4fc3c2c375f42b90aa2`); the
> defensive intent is kept identical and the code is adapted to 5.x idioms. There is no
> official 5.6 build to validate against; the strongest available cross-check is that the
> behavioural test deltas are identical in identity to the already-validated 7.3 backport
> (which was itself cross-checked against official 7.4).

- Patch: `scratchpad/patches/php-5.6.patch` — applies with `patch -p1 --forward --batch`
  on a pristine `php-5.6.40` tree. **8 files, +108/-63.**
- Source: php-5.6.40, sha256 `56fb9878d12fdd921f6a0897e919f4e980d930160e154cbde2cc6d9206a27cac`
  (verified before use).
- Docker image: **`btport-56`** — base **`debian:buster`**, **gcc 8.3.0** (Debian 8.3.0-6),
  native arm64 (no `--platform`). buster is EOL so apt is pointed at `archive.debian.org`.
  Minimal configure: `--disable-all --enable-cli --enable-session --enable-ctype
  --enable-tokenizer --with-pcre-regex`.

## Items that MAP to 5.6 (done)

### 1. OOM no longer longjmps — `Zend/zend_alloc.c` (CVE-2026-109618 core)
- `zend_mm_safe_error()` ended with `zend_bailout()` after a `zend_try{ zend_error_noreturn }
  zend_catch{}` block. **Removed the bailout.** Factored a new helper
  `static void zend_mm_safe_error_ex(const char *format, ...)` that reuses the function's
  existing filename/lineno logic (`zend_is_compiling()` / `zend_get_compiled_filename()` /
  `EG(in_execution)` / `EG(active_op_array)` / `EG(opline_ptr)` — all via `TSRMLS_FETCH()`),
  prints `"\nFatal error: <formatted msg> in <file> on line <n>\n"` to stderr, and calls
  **`_exit(1)`**. `zend_mm_safe_error()` now just frees `heap->reserve` (as before) and tail-calls
  the helper. Semantics mirror the official `zend_mm_safe_error_ex`.
- `ZEND_NORETURN` is **not defined** in 5.6, so the helper is marked noreturn with the same
  guarded `__attribute__((noreturn))` idiom 5.6 already uses for `zend_mm_panic`.
- `<stdarg.h>` for `va_list`/`vfprintf` is already pulled in via `zend.h`.

### 2. Integer-overflow allocation sites — `Zend/zend_alloc.c`
- The **6** `safe_address()` overflow guards (x86, x86_64, arm, aarch64, 32-bit-with-long64,
  portable-double variants) all did
  `zend_error_noreturn(E_ERROR, "Possible integer overflow in memory allocation (%zu * %zu + %zu)", ...)`
  → redirected to `zend_mm_safe_error_ex(...)`.
- Also redirected `_safe_emalloc_string()`'s
  `zend_error_noreturn(E_ERROR, "String allocation overflow, max size is %d", INT_MAX)` — same
  `safe_address()` allocation-abort family, 5.x-specific (no 7.x equivalent). Adapted in-family;
  flagged here for transparency. (32-bit-only path; not exercised on the arm64 test build.)
- Because `safe_address()` is `static inline`, its (now redirected) overflow guard is inlined into
  every consumer — `_safe_emalloc`, `_safe_malloc`, `_safe_erealloc`, `_safe_realloc`,
  `_safe_emalloc_string`, `_estrdup`, `_estrndup`, `zend_strndup` — so all of them route an
  allocation-size overflow through `_exit` (confirmed in the disassembly: 11 `bl` sites to the
  helper).

### 2b. `zend_mm_safe_error_ex` exported `ZEND_API` + `zend_strtod.c` Balloc redirect (parity with 5.4)
- `Zend/zend_alloc.c`: the helper is declared/defined **`ZEND_API`** (was `static`), keeping the
  same guarded `__attribute__((noreturn))` forward-decl idiom.
- `Zend/zend_alloc.h`: added `ZEND_API void zend_mm_safe_error_ex(const char *format, ...);`
  (plain decl, inside `BEGIN/END_EXTERN_C`, before `END_EXTERN_C()`), so other TUs can call it.
- `Zend/zend_strtod.c`: `Balloc()`'s malloc-failure site
  `zend_error(E_ERROR, "Balloc() failed to allocate memory")` → `zend_mm_safe_error_ex(
  "Balloc() failed to allocate memory")`. Balloc's allocation-failure path is exactly the
  "longjmp out of OOM" class the CVE targets, so it is now off the `zend_bailout` path too.
  5.6's `Balloc` has a **single** MALLOC branch (one such site), not the `#if`/`#else` pair; the
  other `Balloc()` message, `"Balloc() allocation exceeds list boundary"` (a `k > Kmax` bounds
  check, not an OOM) is left unchanged, matching the 5.4 sibling. `zend_strtod.c` sees the decl
  via `zend_operators.h` → `zend.h` → `zend_alloc.h`.

### 3. `zend_mm_panic` — `exit(1)` → `_exit(1)`.
  (`zend_out_of_memory` does **not exist** in 5.6's old allocator → N/A, see below.)

### 4. rfc1867 multipart hardening — `main/rfc1867.c` + `main/main.c`
- New INI `PHP_INI_ENTRY("max_multipart_body_parts","-1",PHP_INI_SYSTEM|PHP_INI_PERDIR,NULL)`
  in `main/main.c`.
- `rfc1867_post_handler`: added `int body_parts_cnt = INI_INT("max_multipart_body_parts");`
  (+ `int body_parts_limit` hoisted to the declaration block to avoid any
  declaration-after-statement issue in C89). After the post_max_size check: if `< 0`,
  `body_parts_cnt = PG(max_input_vars) + upload_cnt`; `body_parts_limit = body_parts_cnt`.
  Inside the per-part `Content-Disposition` branch: `if (--body_parts_cnt < 0) {
  php_error_docref(NULL TSRMLS_CC, E_WARNING, "Multipart body parts limit exceeded %d. ...",
  body_parts_limit); goto fileupload_done; }`.
- `multipart_buffer_headers`: added `php_mime_should_save_hdr()` (keep only `Content-Disposition`
  / `Content-Type`) + forward-decl of `php_mime_get_hdr_value()`; the save block now skips
  non-whitelisted headers **and** duplicates, and casts `isspace((unsigned char)*value)`.
  Uses 5.6's `smart_str` (not 7.x `smart_string`).
- `substring_conf`: `int len`/`int i` → `size_t`; caller `php_ap_getword_conf` now passes
  `(size_t)(strend - str)`.

### 5. Session upload-progress neutralised — `ext/session/session.c` (CVE-2026-109619)
- `php_session_rfc1867_callback`: `if (!PS(rfc1867_enabled))` → `if (!PS(rfc1867_enabled) || 1)`
  (C89 — `1`, not `true`). Disables the demonstrated early session producer/consumer.

### 6. SAPI / request-state NULLing (CVE-2026-109619)
- `main/SAPI.c` `sapi_deactivate`: after each `efree()` of `auth_user`, `auth_password`,
  `auth_digest`, `content_type_dup`, `current_user`, set the field to `NULL`. **All five needed
  it** — in 5.6 `sapi_deactivate` did not null any of them (the `=NULL` at lines 570-571 is in
  the separate `sapi_initialize_empty_request`, not this function).
- `main/main.c` `php_request_shutdown`:
  - `http_globals` dtor loop — added `PG(http_globals)[i] = NULL;` after `zval_ptr_dtor(...)`.
    This is the 5.x equivalent of the official `ZVAL_UNDEF`. The read was null-guarded
    (`if (PG(http_globals)[i])`) but the pointer was left dangling after the dtor, so the
    stale request global could be reused before the next `php_request_startup()`; NULLing closes
    that window.
  - Added `PG(modules_activated) = 0;` at the end of the function (it was not reset there).

### 7. `Zend/zend_llist.c` `zend_llist_destroy`
- Added `l->head = NULL; l->tail = NULL;` before `l->count = 0;` (prevents reuse of freed list
  head/tail).

## Items that are N/A for 5.6 (not forced; reasons)

- **`array_init_singleton` / `zend_new_array_singleton` / `HT_HASH_RESET` small-table guard**
  (`Zend/zend_API.h`, `Zend/zend_hash.c`/`.h`, `Zend/zend_types.h`, `main/php_variables.c`
  `array_init`→singleton): 5.6 uses the OLD `HashTable` (`Bucket **arBuckets`), has no
  `zend_string` and no SIMD `HT_HASH_RESET`. The hash over-read these guard against does not
  exist. **Skipped entirely.**
- **`zend_vm_def.h` / `zend_vm_execute.h` concat length check**: 5.6's CONCAT is implemented via
  `concat_function()` in `zend_operators.c` over old `zval` strings (`Z_STRVAL`/`Z_STRLEN`, `int`
  lengths), not per-spec VM handlers using `zend_string_extend`. The 7.x `ZSTR_LEN > SIZE_MAX -
  ...` guard has no faithful, safely-verifiable analog here, so per the brief ("apply only if you
  can do it safely… otherwise N/A, do not guess") this is **N/A**. Note the allocation-overflow
  longjmp that this class ultimately guards is already covered: concat allocates through
  `safe_emalloc`/`_safe_emalloc_string` → `safe_address()`, whose overflow sites are redirected to
  `_exit` by item 2.
- **`zend_out_of_memory`**: does not exist in 5.6's old allocator; the OOM-reporting path is
  `zend_mm_safe_error`, handled by item 1. **N/A.**
- **`zend_multiply.h` redirect**: 5.6's `zend_multiply.h` contains only the
  `ZEND_SIGNED_MULTIPLY_LONG` macros — no `"Possible integer overflow"` site. The allocation
  overflow checks live in `zend_alloc.c` `safe_address()` (covered by item 2). **N/A.**
- **`shutdown_executor` user-handler / object-store resets** (7.x `EG(user_error_handlers)`,
  `EG(user_exception_handlers)`, `EG(objects_store).object_buckets`, `EH_NORMAL`, `ZVAL_UNDEF`
  of user handlers): 5.6's `shutdown_executor` has a different layout and lacks these exact
  fields/types. The request-state resets relevant to CVE-2026-109619 are covered by items 5-6.
  **Skipped the 7.x-specific `EG()` resets.**

## Remaining longjmp sites — status

- **`Zend/zend_strtod.c` `Balloc()` malloc-failure** — **now REDIRECTED** (see item 2b). The
  earlier caveat is resolved; this brings 5.6 to parity with the 5.4 sibling. The only remaining
  `Balloc()` fatal, `"Balloc() allocation exceeds list boundary"`, is a `k > Kmax` bounds check
  (not an allocation/OOM failure) and is intentionally left on `zend_error`, matching 5.4.
- `Zend/zend_hash.c:77` `zend_bailout()` is inside `_zend_is_inconsistent`, a **ZEND_DEBUG-only**
  HashTable consistency checker — not an allocation path, absent from release builds. Untouched
  (out of scope, confirmed by the coordinator).

### d. Behavioural checks

| check | pristine | patched |
|-------|----------|---------|
| `php -i \| grep max_multipart_body_parts` | absent | `max_multipart_body_parts => -1 => -1` |
| `ini_get("max_multipart_body_parts")` | — | `string(2) "-1"` |
| `nm -D sapi/cli/php \| grep zend_mm_safe_error_ex` | absent | **`T zend_mm_safe_error_ex`** (now exported, `ZEND_API`) |
| `"Multipart body parts limit exceeded"` in binary | 0 | 1 |
| Balloc OOM site → helper (not bailout) | `zend_error`/bailout | `<Balloc>` is among the 11 `bl` callers of `zend_mm_safe_error_ex` (objdump); source no longer calls `zend_error` |
| float/dtoa success path (`printf %.17g M_PI`, `(string)(0.1+0.2)`) | works | works (exit 0) — no regression from Balloc redirect |
| integer-overflow path (`SplFixedArray::setSize(0x2000000000000001)`) | prints fatal, **exit 255** (bailout) | prints same fatal, **exit 1** (`_exit`), no "CONTINUED" |
| OOM path (`memory_limit=8M`, alloc loop) | prints fatal, **exit 255** | prints same fatal, **exit 1** (`_exit`) |

The pristine→255 vs patched→1 exit-code split is the direct signature of the longjmp→`_exit`
change (a `zend_bailout()`/E_ERROR shutdown yields CLI exit 255; `_exit(1)` yields 1). The fatal
message text is unchanged, and already-emitted stdout is preserved because 5.6 CLI writes stdout
via `write(STDOUT_FILENO,...)` (`PHP_WRITE_STDOUT`), not libc-buffered — so `bug67247.phpt` (which
exercises the redirected overflow path) still **passes**.

**Multipart part-limit — directly exercised** (CLI runs `rfc1867_post_handler`; a crafted
`--POST_RAW--` multipart with 3 parts was run through `run-tests.php`):
- `max_multipart_body_parts=2` → only parts `a`,`b` registered, part `c` rejected with
  `Warning: Unknown: Multipart body parts limit exceeded 2. To increase the limit change
  max_multipart_body_parts in php.ini.` — **PASS.**
- default (`-1` → `max_input_vars + max_file_uploads`) → all 3 parts kept — **PASS.**

### What could NOT be verified
- No real FPM/web request was issued (FPM harness not set up); the multipart limit was proven via
  the CLI SAPI test path (which does invoke `rfc1867_post_handler`), per the brief's accepted
  fallback.
- Build/test used the minimal `--disable-all` config; interaction of the `_exit` path and
  request-state resets with other extensions (opcache, etc.) was not exercised.
- No end-to-end RCE PoC was run; the longjmp removal is verified structurally (no `zend_bailout`
  on the alloc-error path) and behaviourally (exit-code / `_exit`, no post-error continuation).
- The `Balloc()` OOM site redirect is verified structurally (objdump shows `<Balloc>` calling
  `zend_mm_safe_error_ex`; source no longer calls `zend_error`) and via the dtoa success-path
  smoke test; a genuine `Balloc` malloc failure is not force-triggerable at runtime (tiny early
  dtoa allocation), so its `_exit` was not exercised live — but it shares the identical, live-
  verified `_exit(1)` mechanism as the integer-overflow/OOM paths above.
