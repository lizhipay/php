# PHP 7.0.33 — session hardening (`session.harden`)

## allowed_classes C API
**The `set` function is NOT present in 7.0.**
`grep php_var_unserialize_set_allowed_classes ext/standard/php_var.h` → no match.
(The brief stated this API "was added in 7.0"; in fact it first appears in **7.1**.
In 7.0 the var_hash struct has no `allowed_classes` field and there is no setter.)

**But full object-deny is still achievable in 7.0**, via a different API:
`PHPAPI int php_var_unserialize_ex(zval *, const unsigned char **, const unsigned char *, php_unserialize_data_t *, HashTable *classes)`
is declared in `ext/standard/php_var.h`, and `unserialize_allowed_class()` in
`ext/standard/var_unserializer.re` returns **0 (deny)** when `classes` is a
non-NULL **empty** HashTable → the object becomes `__PHP_Incomplete_Class`
(no autoload, no `__wakeup`/`__destruct`). `php_var_unserialize(a,b,c,d)` is itself
just `php_var_unserialize_ex(a,b,c,d,NULL)`.

### Decision taken (please review)
The brief's fallback said: *"if 7.0 lacks the set function, do upload_progress
sanitisation only."* I did **not** stop at upload_progress-only, because:
1. The brief's stated intent is to neutralise the object-injection RCE, and its
   build-gate section lists **only 5.x** as the "no object-deny" case (expecting
   7.0 to have it).
2. 7.0 genuinely can deny all classes via `php_var_unserialize_ex` with an empty
   HashTable — the same end result as the 8.2/7.1 setter, just a different call.

So 7.0 gets **full object-deny** (implemented with `php_var_unserialize_ex`), which
is strictly stronger than upload_progress-only and passes the `harden=1 blocked`
gate. If you specifically want the literal upload_progress-only variant instead,
it's a quick swap — say so.

## What mapped from 8.2 → 7.0
| 8.2 reference | 7.0 implementation |
|---|---|
| `bool harden;` in `php_ps_globals` | `zend_bool harden;` |
| INI `session.harden` `PHP_INI_SYSTEM` `OnUpdateBool` | identical |
| `static HashTable *php_session_no_classes` + alloc in MINIT | identical |
| set empty allowed-classes on var_hash before unserialize | **no setter in 7.0** → each of the 3 decoders now calls `php_var_unserialize_ex(..., &var_hash, (PS(harden) && php_session_no_classes) ? php_session_no_classes : NULL)` instead of `php_var_unserialize(..., &var_hash)` |
| upload_progress key `\|`/`!` → `_` under `PS(harden)` | identical bytes |

Notes:
- No shared `php_session_unserialize_init()` helper and no `in_rfc1867_update`
  field in 7.0 (both are 8.x) — 3 inline decoders, handled at each call site.
- `harden=0` passes `classes = NULL`, which is byte-for-byte the original
  `php_var_unserialize` behaviour, so stock PHP semantics are preserved. Default off.

## upload_progress key sanitisation
Implemented identically to the proven 8.2 patch (same bytes). Not exercised at
runtime: the rfc1867 multipart-upload path only fires in web SAPIs (fpm/cgi), not
in the CLI SAPI used for the build gate, so it is verified by code-identity with
the 8.2 reference. The decisive runtime gate for 7.0 is the object-injection test
above, which passes (full object-deny confirmed).
