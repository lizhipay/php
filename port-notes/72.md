# PHP 7.2.34 backport notes — CVE-2026-109618 / CVE-2026-109619

"Avoid state corruption via bailout" (upstream 7.4 commit 712e60f9), backported to
the last 7.2 release (7.2.34). Reference template: `patches/php-7.4.patch`.

- Source: php-7.2.34.tar.gz, sha256 `8b2777c741e83f188d3ca6d8e98ece7264acafee86787298fae57e05d0dddc78` — **verified before extract**.
- Patch: `patches/php-7.2.patch` (header comment + unified diff, `a/`…`b/` paths).
- Build base image: **`btport-72`** = `debian:bullseye` (gcc 10.2.1) + build-essential,
  autoconf, pkg-config. bullseye chosen per the brief (gcc-14/trixie is too new for 7.2;
  the prebuilt `btphp-harness` is trixie/gcc-14 and lacks re2c/bison, so not reused).
  apt sources were pointed at `snapshot.debian.org/.../20260824T000000Z` because the live
  `bullseye-security` pool 404s on the local mirror while the base image already carries
  the security-version libc6 (version skew otherwise).
- Note on environment: Docker bind mounts do not propagate the host FS in this sandbox
  (even `/tmp` mounts come up empty), so both trees were loaded with `docker cp` into a
  persistent container `bt72` and built/tested there.

## Files changed
16 of the 17 files the 7.4 patch touches. `Zend/zend_types.h` is intentionally **not**
changed (see dropped sub-hunk below). Everything else is semantically identical to 7.4.

## Adapted sub-hunks (symbol/structure differences vs 7.4)

1. **Zend/zend_types.h — HT_HASH_RESET small-table fix: DROPPED (not applicable).**
   7.4's hunk adds a `size < 64` memset branch to an SSE/`__m128i` fast path. In 7.2
   `HT_HASH_RESET` is already a single unconditional
   `memset(&HT_HASH(ht,(ht)->nTableMask), HT_INVALID_IDX, HT_HASH_SIZE(...))` with **no
   SSE fast path**, so it already handles tables with hash size < 64 correctly. The 7.4
   bug (SSE loop asserting size>=64 and a multiple of 64) does not exist in 7.2. Porting
   it would be a no-op at best; dropped and recorded.

2. **VM concat guards use `ZEND_SIZE_MAX`, not `ZSTR_MAX_LEN` (symbol absent in 7.2).**
   `ZSTR_MAX_LEN` does not exist in 7.2. 7.2's own overflow idiom (see
   `concat_function` in `Zend/zend_operators.c`) is `op1_len > SIZE_MAX - op2_len`. The
   ported guards use `ZEND_SIZE_MAX` (defined in `Zend/zend_types.h`, guaranteed present)
   which is semantically the same and prevents the `len + ZSTR_LEN(op2_str)` wrap that
   feeds `zend_string_extend`/`zend_string_alloc`. Message string kept identical
   ("Integer overflow in memory allocation") and routed to `zend_mm_safe_error_ex`.

   Also: 7.2's inline concat handlers have **no** pre-existing overflow check in either
   branch (7.4 had one in the "extend" branch from an older fix). To reach the same final
   state as patched 7.4, a guard was **added** to both the extend branch and the fast-path
   `else`/alloc branch of every concat handler. The FAST_CONCAT *slow-path* trailing alloc
   was left unguarded, matching upstream (7.4 did not guard its equivalent site).
   Guards added: `zend_vm_def.h` 2 extend + 2 else-alloc; `zend_vm_execute.h` 18 extend +
   18 else-alloc (9 FAST_CONCAT slow-path allocs correctly left alone). `zend_vm_execute.h`
   is generated but edited directly, as the brief instructs (no regeneration).

3. **ext/session/session.c — rfc1867 neutralisation uses `|| 1`, not `|| true`.**
   7.4 writes `if (!PS(rfc1867_enabled) || true)`. 7.2's session.c unit has no C99
   `true` in scope → `error: 'true' undeclared` at compile. Changed to `|| 1`
   (identical always-true semantics, 7.2-idiomatic). *This was caught by the compile gate.*

4. **Zend/zend_execute_API.c — shutdown_executor placement adapted to 7.2 structure.**
   7.2's `shutdown_executor` is laid out differently from 7.4 (object storage is freed
   near the top; the fast-shutdown path is `if (fast_shutdown){...}` and the full-cleanup
   path is its `else`). The three resets were placed to preserve upstream intent:
   - `EG(error_handling)=EH_NORMAL; EG(exception)=NULL;` — unconditional, immediately after
     `zend_objects_store_free_object_storage(...)` (as in 7.4, before the extension
     deactivators run).
   - In the `if (fast_shutdown)` branch (7.2's equivalent of 7.4's new fast-path `else`
     branch, where the handler stacks are otherwise not cleaned): `ZVAL_UNDEF` the user
     error/exception handlers and `memset` the three handler stacks to 0, plus
     `EG(objects_store).object_buckets=NULL; EG(objects_store).top=1;`.
   All referenced fields/enums exist in 7.2 (verified: `EG(error_handling)`, `EH_NORMAL`,
   `EG(exception)`, `EG(objects_store).object_buckets/.top`, the three `zend_stack` handler
   stacks — memset-zeroing a `zend_stack` empties it, matching 7.4; request heap is freed
   wholesale in fast shutdown so no leak).

5. **Zend/zend_hash.c / zend_hash.h — `zend_new_array_singleton()` built on 7.2 API.**
   7.4 adds it right after `_zend_new_array_0`, which does not exist in 7.2. 7.2 creates
   arrays via `_array_init` → `ZVAL_NEW_ARR` + `_zend_hash_init(...)`. The ported function
   mirrors that: `emalloc(sizeof(HashTable)); zend_hash_init(ht,0,NULL,ZVAL_PTR_DTOR,0);
   ht->nTableSize = 1;`. `array_init_singleton` in `zend_API.h` is defined exactly as 7.4
   (`ZVAL_ARR((arg), zend_new_array_singleton())`; `ZVAL_ARR` confirmed present in 7.2).
   This yields the intended size-1 GPC arrays (memory-amplification hardening).

## Validation

### (a) Patch applies
`patch -p1 --forward --batch` on a **fresh** 7.2.34 extract: **exit 0, 0 `.rej`, 0 `.orig`**,
all 16 files. The applied tree is byte-identical to the hand-edited tree (`diff -rq`:
IDENTICAL).

### (b) Compile (btport-72 / bullseye / gcc 10.2.1, `make -j8`)
configure: `--disable-all --enable-cli --enable-session --enable-tokenizer
--with-pcre-regex --enable-ctype --enable-json`.
- Pristine: **BUILD_OK**, `sapi/cli/php` → PHP 7.2.34 (cli).
- Patched:  **BUILD_OK**, `sapi/cli/php` → PHP 7.2.34 (cli). No new errors in our files
  (only a pre-existing unrelated `readdir_r` deprecation warning in mod_files.c, present
  in pristine too). The one compile failure encountered (`'true' undeclared`) was fixed by
  adaptation #3 and the patch regenerated.

### (c) make test (NO_INTERACTION=1), pristine vs patched
Full suite, `--disable-all` build (so ~6.9k of 15932 .phpt are skipped as their
extensions aren't built).

First run (both suites ran **concurrently** in one container — this made the
port-binding `php_cli_server_*` / interactive-CLI tests flaky on BOTH sides):
| | run | passed | failed | skipped |
|---|---|---|---|---|
| pristine | 9034 | 8971 | 32 | 6898 |
| patched  | 9033 | 8950 | 52 | 6899 |

The +20 patched failures were dissected by re-running each newly-failing test
**sequentially and in isolation** on both binaries:
- `tests/basic/bug67198`, `ext/standard/tests/streams/bug70198`,
  `sapi/cli/tests/bug43177`, `sapi/cli/tests/bug61679`, and all
  `sapi/cli/tests/php_cli_server_0*` → **PASS on both** in isolation. Pure
  concurrency flakiness (two suites competing for TCP ports/CPU), not the patch.
- `ext/session/tests/rfc1867*.phpt` (×8) → **fail on patched only — INTENDED.**
  These assert `$_SESSION["upload_progress_..."]`, populated by the session
  rfc1867 callback that this fix neutralises (`|| 1`). Disabling session upload
  progress is exactly the CVE-2026-109619 "consumer" mitigation. They also POST
  multipart data, so they confirm the `array_init_singleton` `$_POST` path works
  (the diff is limited to the upload_progress line; `$_POST` parsing is fine).
- `tests/lang/bug45392.phpt` → **fail on patched only — expected OOM-output
  delta.** It does `ob_start()` then hits `memory_limit`; with buffering active
  pristine prints `…\nFatal error` (no blank line), whereas `zend_mm_safe_error_ex`
  (a fixed `fprintf(stderr,"\nFatal error: …")`, verbatim from upstream 7.4) always
  emits one leading `\n`, adding a blank line here. This is inherent to the fix
  routing OOM through a fixed-format printer instead of `php_error_cb`; the brief
  lists OOM test deltas as expected. The common no-`ob` OOM case (e.g.
  `Zend/tests/bug55509`, and 9 other OOM tests in the suite) matches pristine and
  passes.

Net real delta beyond flakiness: **9 pre-existing tests flip pass→fail = 8 intended
rfc1867 (upload-progress disabled) + 1 expected OOM-output cosmetic (bug45392).**
No functional regression.

Clean fully-sequential re-run (no concurrency), noise-free totals:

### (d) Behavioural checks
- `nm sapi/cli/php | grep zend_mm_safe_error_ex` → **present** (`T zend_mm_safe_error_ex`)
  in patched; **absent** in pristine.
- `php -i | grep max_multipart_body_parts` → `max_multipart_body_parts => -1 => -1`
  (patched); `ini_get` default `-1`, settable (`-d …=42` → `42`). In pristine the INI is
  unknown (`ini_get` → `bool(false)`).
- OOM mechanism (the core of CVE-109618): `php -d memory_limit=8M -r '$x="A";while(1){$x.=$x;}'`
  - pristine: "Fatal error: Allowed memory size … exhausted …", exit code **255**
    (zend_bailout + normal shutdown — the vulnerable path).
  - patched:  same fatal-error text, exit code **1** (`zend_mm_safe_error_ex` → `_exit(1)`;
    no bailout, shutdown never processes the invalid state).
- Multipart part-limit (`max_multipart_body_parts`): the CLI SAPI does not parse multipart
  bodies, so a live rejection needs FPM/Apache (not built here). Verified at CLI level: the
  INI exists, defaults to `-1` (→ resolved at runtime to `PG(max_input_vars)+max_file_uploads`
  inside `rfc1867_post_handler`), and is overridable. The enforcement code
  (`if (--body_parts_cnt < 0){ warn; goto fileupload_done; }`) is present in the patched
  `main/rfc1867.c`. **Live multipart rejection: not exercised (unverified).**

## Honest status
Full port. One sub-hunk dropped with reason (HT_HASH_RESET — not applicable to 7.2).
Three sub-hunks adapted (ZEND_SIZE_MAX for concat; `|| 1` for session; shutdown_executor
placement) and one reimplemented on the 7.2 array API (`zend_new_array_singleton`), all
semantically equivalent to upstream. `zend_mm_safe_error_ex` is kept verbatim from
upstream (leading `\n`), matching pristine's common-case OOM output.

Pass→fail test flips are all accounted for: 8 intended (session upload-progress disabled)
+ 1 expected OOM-output cosmetic (bug45392, ob_start+OOM) + several `php_cli_server`/CLI
tests that were concurrency flakiness and pass in isolation on both trees.

Not verified: (1) a live multipart over-limit HTTP rejection — CLI SAPI cannot drive a
multipart POST, so only the INI default/override and the enforcement code path were
confirmed, not an end-to-end 413-style rejection; (2) noise-free full-suite totals from a
single sequential run (the per-test isolation diffs are the authoritative signal instead).
