## Adapted hunks (3 files) — reasons + what changed

### 1. Zend/zend_alloc.c — `#include "zend_execute.h"` (context adaptation)
7.4 context is `#include "zend_bitset.h"` immediately followed by a bare `#include <signal.h>`. 7.3 instead has
`#include "zend_bitset.h"` followed by `#ifdef HAVE_SIGNAL_H / # include <signal.h> / #endif`, so the hunk's
trailing context did not match. Added `#include "zend_execute.h"` right after `#include "zend_bitset.h"`
(same position, same effect). All helpers used by the new `zend_mm_safe_error_ex()`
(`zend_is_executing`, `zend_get_executed_filename_ex`, `zend_get_executed_lineno`, `zend_is_compiling`,
`zend_get_compiled_filename`, `zend_get_compiled_lineno`) exist in 7.3 (verified in zend_execute.h /
zend_compile.h). The other 8 zend_alloc.c sub-hunks (new `zend_mm_safe_error_ex`, `zend_mm_safe_error`
rewrite, `_exit` in zend_mm_panic/zend_out_of_memory, 5 overflow-site redirects) applied by offset.

### 2. Zend/zend_execute_API.c — `shutdown_executor()` state reset (layout adaptation)
7.3's `shutdown_executor()` is laid out differently from 7.4: object storage is freed early (before the
fast/slow branch), the fast/slow branch is `if (fast_shutdown){...} else {...}` (inverted vs 7.4), and there is
no `zend_weakrefs_shutdown()` (weakrefs are a 7.4 feature). The 7.4 hunk-1 context (anchored on
`zend_weakrefs_shutdown();`) therefore could not apply. Re-expressed the identical intent manually:
  - Unconditional, right after `zend_objects_store_free_object_storage(...)`:
    `EG(error_handling) = EH_NORMAL; EG(exception) = NULL;`  (same two lines, same position relative to the
    object-storage free that 7.4 uses).
  - In the **fast_shutdown** branch (7.3's equivalent of the new fast-path `else` block 7.4 adds):
    `ZVAL_UNDEF(&EG(user_error_handler)); ZVAL_UNDEF(&EG(user_exception_handler));` plus `memset(...,0,...)` of
    the three handler stacks (`user_error_handlers_error_reporting`, `user_error_handlers`,
    `user_exception_handlers`) — all fields verified present in 7.3's zend_globals.h.
  The slow path already destructs+clears these handlers in 7.3 (via `zval_ptr_dtor` + `zend_stack_clean`),
  matching 7.4's slow path, so no change was needed there. Hunk-2 (`EG(objects_store).object_buckets = NULL;
  EG(objects_store).top = 1;` after `zend_cleanup_internal_classes()` in the fast branch) applied by offset.
  The `zend_weakrefs_shutdown()` line from the 7.4 context was intentionally NOT added (symbol absent in 7.3).

### 3. Zend/zend_vm_def.h + Zend/zend_vm_execute.h — concat overflow guards (symbol + pre-existing-check adaptation)
Two differences from 7.4:
  (a) **`ZSTR_MAX_LEN` does not exist in 7.3** (introduced in 7.4 as `SIZE_MAX - ZSTR_MAX_OVERHEAD`). Using it
      caused `error: 'ZSTR_MAX_LEN' undeclared` in the first build attempt. 7.3's own native concat-overflow
      idiom (zend_operators.c `concat_function`, line ~1850) is `op1_len > SIZE_MAX - op2_len`. Adopted that:
      the guards use `SIZE_MAX - ZSTR_LEN(op2_str)` instead of `ZSTR_MAX_LEN - ZSTR_LEN(op2_str)`. This is the
      version-equivalent symbol, not an invented one; semantics (detect `len1+len2` size_t overflow) are
      identical.
  (b) **7.3 has ZERO pre-existing concat overflow checks** (7.4 had 1 in zend_vm_def.h + 8 in zend_vm_execute.h
      that the patch merely swapped `zend_error_noreturn`->`zend_mm_safe_error_ex`). So the 7.4 "swap" hunks had
      nothing to swap and failed (1 in def, 8 in execute). The "add" hunks applied but, because 7.3's concat
      branches end with `FREE_OP2()` (vs 7.4's `zend_string_release_ex`), fuzzy matching mis-placed some and
      even produced duplicate guards. So both VM files were reset to pristine and regenerated **deterministically**
      to reproduce patched-7.4's exact guarded set:
        - guard EVERY "extend" fast-path branch (`str = zend_string_extend(op1_str, len + ...)`), using `len`;
        - guard ONLY "alloc" branches whose immediately preceding line is `} else {`
          (`str = zend_string_alloc(ZSTR_LEN(op1_str) + ZSTR_LEN(op2_str), ...)`), using `ZSTR_LEN(op1_str)`;
        - leave the flat `FAST_CONCAT` alloc branches (preceded by `break; }`) UNGUARDED.
      This predicate was validated to reproduce patched-7.4 exactly:
        zend_vm_def.h   = 2 extend + 2 else-alloc guarded, 1 flat-alloc unguarded  -> 4 checks (== 7.4)
        zend_vm_execute.h = 17 extend + 17 else-alloc guarded, 9 flat-alloc unguarded -> 34 checks (== 7.4)
      zend_vm_execute.h is the generated file; per the brief it was edited directly, not regenerated.

## Honestly unverified / caveats
  - The "Multipart body parts limit exceeded" **E_WARNING text** was not captured in the e2e harness (it is
    emitted to the built-in server's own stderr during request-startup POST parsing and did not land in the
    log I scraped). The enforcement itself IS proven by the part-count drop (4 vs 10); only the warning-string
    capture is unconfirmed.
  - No FPM/Apache exploit reproduction was attempted; this is a source-level backport + functional test, not a
    full RCE PoC. The OOM `longjmp`-removal is verified structurally (zend_mm_safe_error_ex / _exit call sites)
    and by the OOM-path test behaviour change, not by triggering a live corruption.
  - 7.4 cross-check of the 9 expected-delta failures: see "7.4 upstream confirmation" below.
